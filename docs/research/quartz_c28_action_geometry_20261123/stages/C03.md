# C03 — stable numerical and cost design

No continuum discretization or time-integration solver is introduced. For a fixed finite law, H2 is exact algebra; approximation sources are (i) the statistical latent closure if applied to games, (ii) floating arithmetic and fixed epsilon action selection, and (iii) noisy runtime measurement. These are kept separate. There is no invented step-size convergence study.

Prepare centered support features only on positive masses; point masses use zero feature. Reject nonfinite/negative probability, nonnormalized rows beyond the admitted1e-12 representation tolerance, |r|>=1, negative/nonfinite cost, invalid b,m,horizon. Unsupported observations are explicit failures. The direct formula computes one posterior division per first-action outcome, amortized over remaining second actions. The lifted formula multiplies each affine continuation by its positive likelihood. Both cache the same incumbent-level coefficients and use the same arithmetic type and no-repeat indices.

Theoretical positivity applies for every supported branch with |r|<1. Finite-precision validation has its declared tested range: ordinary |r|<=.99, plus the1-2^-20 stress magnitude, exact/near ties and m endpoints. A bounded value-domain absolute5e-12 comparison is used, with no relative tolerance nearzero. Exact mathematical argmax and native epsilon choice remain distinct. Any mismatch is recorded and diagnosed before continuing; no tolerance inflation.

Cost treatment: affine preparation is inside synthetic invocation timing, and both methods independently pay all GameState cue/initialization/belief/cache/update/planning/query costs. Resident parsing/history replay/serialization are outside and named. Counterbalanced paired order, warmups, multiple iterations for short kernels and fixed source-root aggregation address clock granularity and drift. No estimated timer cost is subtracted. A kernel ratio cannot establish end-to-end playing strength or a wall-cost optimal controller.

Expected arithmetic remains O(n^2) for three utility levels with O(n) prepared data. Lifting trades a per-branch division for extra multiplications in the second-action scan; the runtime crossover is to be measured, not assumed. Next C04 sets bounded execution ownership/resources.
